# Concurrency decomposition: where the cost goes under load

PowDB's single-request query cost is its strength. What happens when many
clients hit one server at once is a separate question, and this document
answers it honestly and reproducibly. It measures p50 latency at concurrency 1
versus concurrency 10 for three workloads, decomposes where the amplification
comes from, and shows what the read-only serving tier does and does not change.

The methodology and script are committed so anyone can reproduce the shape of
these results:
[`scripts/bench-concurrency.sh`](../../scripts/bench-concurrency.sh). This is the
same honest register as [`docs/powdb-vs-sqlite.md`](../powdb-vs-sqlite.md): the
**c10/c1 amplification ratio is the stable, portable signal**; the absolute
microseconds are machine-specific and will move.

## The architecture, honestly

PowDB is single-writer with parallel readers and no MVCC. Three facts about
admission explain every number below:

1. **A single writer takes the whole admission gate.** Every write (autocommit
   or explicit transaction) serializes through one write-admission path. Two
   writers never run at once; the second waits.
2. **Reads run parallel among themselves.** `powdb-server` wraps the engine in
   `Arc<RwLock<Engine>>`, so concurrent reads share a read lock and do not block
   each other on the lock. They still share one process: CPU, the mmap'd heap,
   the allocator, and the server's dispatch path.
3. **An explicit `begin` holds the gate for its whole lifetime**, blocking all
   readers until `commit`/`rollback`. Autocommit statements release admission
   before the fsync wait, so on read-mostly paths autocommit is dramatically
   friendlier to concurrency than a long-held transaction. Keep transactions
   short. (See the transaction guidance in
   [`docs/POWQL.md`](../POWQL.md#transactions).)

The read-only serving tier ([`docs/read-only-serving.md`](../read-only-serving.md))
opens a quiescent directory with **no writer at all**: it never takes the write
admission gate, and it refuses every mutation. That is how you scale reads -
run N independent read-only processes over restored snapshots. The worked
example is [`examples/edge-snapshot-serving/`](../../examples/edge-snapshot-serving/).

## What was measured

- A `~50,000`-row `Event` table (`unique auto id`, so point reads are indexed
  lookups), seeded in one transaction.
- Load generated by **N concurrent Node processes** using the repo's TypeScript
  client (`clients/ts`), each holding a persistent connection. Node was chosen
  over spawning `powdb-cli` per query because a persistent connection isolates
  query latency from process-startup and handshake cost: which is exactly the
  thing we want to keep out of the measurement. Each client records per-request
  wall time; the reported p50 is the median across all samples from all clients
  at that concurrency level.
- Three workloads: **point read** by unique id (indexed), **grouped aggregate**
  (`group .kind` over the full 50K rows), **single-row insert** (default
  `WalSyncMode::Full`, so each commit is fsync-bound: production durability, not
  a RAM-only path).
- The two read workloads were then run against a **`--readonly` server on a
  restored copy** of the same data, where no write gate exists.
- Plus a mixed scenario: one reader's p50 while **9 concurrent writers** hammer
  inserts against the same read-write server.

## Results

Hardware: Apple M5 Max (18 cores), macOS 26.5.1, arm64. PowDB 0.15.0 release
build, `powdb-server` default durability (`WalSyncMode::Full`). Node v24. p50 in
microseconds. Numbers below are from one representative run; the ratios
reproduced within ~0.1-0.2 across repeated runs.

| Workload (server)          |    c1 (us) |   c10 (us) | c10/c1 |
| -------------------------- | ---------: | ---------: | -----: |
| point read (read-write)    |         47 |        139 |  2.96x |
| grouped aggregate (r-w)    |      8,100 |     12,793 |  1.58x |
| single-row insert (r-w)    |      4,042 |      7,192 |  1.78x |
| point read (read-only)     |         45 |        136 |  3.02x |
| grouped aggregate (r-only) |      7,602 |     12,844 |  1.69x |

Mixed: with 9 concurrent writers inserting, a reader's point-read p50 was
**68 us**, versus **47 us** solo: a **1.45x** gate tax on reads while a writer
is present.

## Reading the numbers

**Single-request cost is the strength.** At concurrency 1, a point read is
~47 us and a full-scan grouped aggregate over 50K rows is ~8 ms. That is the
per-op cost the engine is built to win on, and it is what you get on every
read-only serving process, on every host.

**The write gate serializes writes, but group commit softens the curve.**
Ten concurrent inserters do not each pay 10x: the insert p50 rises only ~1.8x
at c10, because PowDB's statement-boundary group commit coalesces the fsyncs of
concurrent commits. The gate still serializes the *logical* admission of each
write; group commit is why the *latency* amplification is well under linear.
The gate's effect on **readers** shows up in the mixed run: a reader sharing the
server with nine writers pays ~1.45x, the cost of interleaving with commits
holding admission.

**Concurrent reads also amplify: and that part is not the write gate.** Point
reads amplify ~3x at c10, and they amplify *by essentially the same factor on
the read-only server* (3.02x) as on the read-write server (2.96x). If this
amplification were the write-admission gate, it would vanish when there is no
writer; it does not. It is concurrent-read contention inside one process
(dispatch, the shared mmap/allocator, CPU scheduling of many in-flight
requests), independent of admission. Diagnosing and, if warranted, reducing this
concurrent-read amplification in the read-only serving tier is scoped as a
follow-up; the read-only tier is the niche where it matters, because that is the
tier built to scale reads.

## Conclusion

- **Single-request cost is the engine's strength.** Reach for PowDB where each
  request is cheap and that cheapness compounds across the request path.
- **Shared read-write concurrency pays at the gate.** Writes serialize through
  one admission path (group commit keeps the latency amplification sub-linear),
  and readers sharing a server with a live writer pay a gate tax. Long explicit
  transactions make this worse because they hold admission for their whole
  lifetime: keep them short, prefer autocommit on read-mostly paths.
- **The read-only serving tier sidesteps the write gate entirely.** No writer,
  no admission, no mutations. You scale reads by running many independent
  read-only processes over restored snapshots: each carries the same per-op
  curve, and you add processes and hosts to add read throughput. The remaining
  within-process read amplification is the same on this tier and is the scoped
  next step.
- **For many concurrent clients over one shared read-write database, use
  Postgres.** That is the workload PowDB deliberately does not target.

## Reproduce it

```bash
./scripts/bench-concurrency.sh
# or, against prebuilt binaries:
POWDB_BIN=/path/to/target/release ./scripts/bench-concurrency.sh
```

Requires Node and the built TypeScript client (`clients/ts/dist`). The script
seeds the table, backs up and restores the read-only copy, starts both servers,
and prints the results table above. Expect the absolute numbers to differ on
your hardware and the ratios to land close.
