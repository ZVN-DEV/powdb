# PowDB v0.13 Plan: Fast Document Reads, Complete JSON, Bounded Joins

Date: 2026-07-14
Status: DRAFT FOR IMPLEMENTATION
Target: v0.13.0
Includes: the unreleased v0.12.1 query-cancellation work and its full verification gate

## 1. Release thesis

v0.13 makes the document path introduced in v0.12 fast and complete enough for the reference
document workload to re-benchmark PowDB as a primary store. The release has three jobs:

1. Make remote document reads competitive with typed-row reads, both for one request and
   under concurrent connections.
2. Finish the JSON query surface: indexed filter/order, aggregate/group/order expressions,
   typed results, and SQL arrow operators.
3. Finish cooperative cancellation and remove the compound-join planning foot-gun it bounds.

This is a larger release than the original v0.13 in the approved 2026-07-13 document-store
design. That plan estimated about three weeks for expression indexes, symmetric aggregates,
wire type hints, and SQL arrows. The document-read fast path, binary typed results, TCP read
parallelism, ordered path scans, and compound-join planning expand the realistic build to
about five weeks with parallel lanes.

The stop condition is not "all APIs exist." The release is done when the reference
workload can remove its remaining app-side document sort/group work, remote document point
reads no longer pay the legacy text conversion path, healthy reads scale across connections,
and a compound `ON` clause cannot select an unbounded quadratic plan when an equi-join key is
available.

## 2. Evidence and current baseline

### 2.1 What the reference validation proves

The July 2026 validation evidence establishes these results on 9,270 parent records and 18,579
version records:

- Correctness parity is achievable: 21/21 against the reference relational baseline.
- v0.11 overflow pages removed app-side chunking and survived WAL recovery validation.
- v0.12 native JSON removed the 77,519-row EAV hot-column table, reduced schema from eight
  types to seven and indexes from 23 to 16, and reduced reload time from 16.5s to 5.55s.
- Path filters and projections work, but without path indexes they remain scans.
- `group .data->...` and `order .data->...` still fail at the parser, leaving group and sort
  work in the application.
- Direct path extraction collapses a missing path and explicit JSON null to the same legacy
  wire text `"null"`. Separately, `json_type()` returns a string `"null"` for explicit JSON
  null while a missing path's `Empty` also renders as `"null"`; the legacy wire cannot tell
  those cells apart. A present JSON string whose value is literally `"null"` creates a third
  ambiguous legacy text cell.
- On v0.12.0, a compound-ON join ignored the 30s timeout, survived disconnect, and held the
  global gate until restart.

The informal v0.12 probes are directional, not release baselines:

| Shape | Earlier cycle p50 | v0.12 informal probe |
|---|---:|---:|
| JSON filter | 1,742ms | about 231ms |
| Deep document read | 443ms | about 123ms |
| Filter and sort | 673ms | about 107ms |

### 2.2 New findings grounded in the current code

Two new read costs are real in the code even though their exact measurements are not in the
the supplied validation evidence:

- `Value::Json::to_wire_string()` calls `pj1_to_text()` for every returned JSON cell.
  `QueryResult::Rows` then converts every cell to a string in the server. Returning the
  complete document over the legacy result frame therefore requires a full PJ1 walk and a
  canonical text allocation on every read.
- The engine already supports concurrent `&self` execution behind `RwLock::read`, but every
  bare wire query first acquires the single-permit transaction semaphore. Healthy TCP reads
  therefore serialize before they can reach the shared engine read lock.

The supplied measurement reports about 24ms for a roughly 2.5KB document point read, a desired
roughly 2ms target, and a roughly 9.7x wall at ten connections. Those measurements must be
captured in a checked-in benchmark artifact before code changes. They are targets to verify,
not numbers established by the supplied validation evidence.

### 2.3 Unreleased v0.12.1 work folds into v0.13

v0.12.1 was never fully released. That is now intentional: its cancellation work is part of
v0.13 rather than a separate public dependency. Before the rest of v0.13 builds on it, the
combined release gate must prove all three original runaway-query symptoms are bounded:

1. A configured query deadline stops the compound nested-loop execution and releases the
   engine lock and transaction permit.
2. Client disconnect stops the issuing query rather than merely dropping its eventual reply.
3. A concurrent healthy read succeeds after timeout/disconnect without restarting the server.

The live `fix/v0.12.1-query-cancellation` branch contains cooperative timeout polling in scan,
join, group, and mutation loops. At the time this plan was written, timeout signaling is
visible, but an end-to-end server path that triggers `CancelReason::Disconnect` is not yet
demonstrated. v0.13 must finish and verify that path before release.

Cancellation remains the safety backstop. The v0.13 compound-join work also changes the bad
plan shape so the exact regression query completes normally without needing cancellation.

## 3. Scope and priority

### Tier 0: safety baseline folded in from the unreleased patch

0. Cooperative timeout, client-disconnect cancellation, and prompt lock/admission release for
   scans, joins, groups, and mutations. This must be green before parallel v0.13 feature lanes
   build on the execution engine.

Mutation cancellation preserves statement atomicity. Target discovery and the final pre-write
boundary are cancellable. After the first write, the statement finishes without polling because
the storage layer does not yet provide a statement savepoint that can undo a logged prefix. A
timed-out or disconnected wire query inside an explicit transaction rolls back the whole
transaction before releasing its admission permit.

### Tier 1: reads, the release-defining work

1. Expression and JSON-path indexes, including ordered index scans.
2. Selective document reads plus an opt-in binary typed result wire.
3. Concurrent autocommit reads that bypass the writer transaction gate safely.

### Tier 2: finish the JSON and aggregate surface

4. Expression-valued aggregate, group, order, and related keys.
5. Symmetric PowQL aggregates with explicit raw SQL semantics.
6. SQL `->` and `->>` lowering.

### Tier 3: robustness and DX

7. Compound-ON equi-key extraction and bounded pure nested loops.
8. Targeted unsupported-path errors for any positions still outside v0.13.

Tier 1 is non-negotiable. If schedule pressure forces a cut, v0.13 should delay as a whole
rather than ship expression indexes while the unvalidated document point-read and concurrent
read performance gaps remain release blockers. The optional grouped raw-byte optimization is
the first deferrable item because it does not block the reference re-benchmark.

The sweep free-ratio auto-trigger from the earlier v0.13 phasing is explicitly deferred. Manual
and post-recovery sweep remain supported. An automatic trigger needs its own locking, stall,
observability, and crash-safety design and is unrelated to the remaining release blockers.

## 4. Decisions that must be locked before implementation

### D13.1: Native path-index syntax follows PowQL DDL

Use:

```powql
alter Post add index (.data->"author"->"name")
alter Post add unique (.data->"externalId")
```

The prior design's `create index on posts (...)` syntax conflicts with PowQL's established
`alter <Type> add index` DDL and with the public language guide. SQL may expose `CREATE INDEX`
through the SQL frontend; native PowQL should not grow a second DDL family.

Parentheses make the indexed expression boundary explicit and leave room for wider expression
indexes later. v0.13 validates only a JSON path rooted at a stored JSON column.

### D13.2: Sorted path reads are part of expression indexes

The reports prove that native path ordering is required, but they do not by themselves prove
that an ordered index scan is required. The stronger performance claim is an architectural
inference from the filter/sort shape and the release thesis. The earlier design covers
equality/range extraction but not a full ordered index scan. v0.13 adds an ordered
expression-index plan/runtime path so:

```powql
Post order .data->"publishedAt" desc limit 20
```

can walk the index in order and stop after K rows without materializing and sorting the table.

### D13.3: Document-read optimization and typed wire are one lane

Column type hints alone cannot meet the document-read target. If the server returns JSON text, some
component must walk PJ1 and allocate that text. v0.13 therefore reopens approved door D11 and
ships an additive typed result path with binary cells.

Legacy `Query`/`QuerySql`/`QueryWithParams` and `ResultRows` frames remain byte-for-byte
unchanged and keep string results. New clients opt in with typed query frames and receive typed
row/scalar frames. This avoids relying on connection-version guessing because the current
handshake reports only the server version and has no client capability negotiation.

The additive V1 frame tags are frozen as `0x13` native PowQL query, `0x14` native
parameterized PowQL query, `0x15` native SQL query, `0x16` native rows, and `0x17` native
scalar. These tags do not overlap legacy query/result frames, connection control, or sync
control.

Typed cells carry their actual `TypeId` plus a length-delimited binary body. `Empty` has a tag
and no body. JSON carries canonical PJ1 bytes, and Bytes carries its exact bytes. A declared
column type vector is deliberately absent from V1 because JSON-path projections can produce
different scalar types across rows; each cell tag is authoritative.

Each cell is `[type:u8][body_len:u32 LE][body]`. Fixed bodies are signed `i64` for Int,
IEEE-754 `f64` for Float, one byte (`0` or `1`) for Bool, signed `i64` microseconds for
DateTime, and 16 raw bytes for Uuid. Str is UTF-8; Bytes and Json preserve exact bytes.
Cell tags reuse the stable storage `TypeId` representation: `0` Empty, `1` Int, `2` Float,
`3` Bool, `4` Str, `5` DateTime, `6` Uuid, `7` Bytes, and `8` Json.

The TypeScript client decodes typed cells directly to JS values. It decodes PJ1 directly to a
JS JSON value without a server `pj1_to_text()` plus client `JSON.parse()` round trip.

Recommended client surface:

```ts
const result = await client.queryNative(query, params);
```

`query()` remains the legacy string API. Existing `queryTyped(query, schema)` remains source
compatible and may use the native frame when available, then apply or validate the caller's
schema.

### D13.4: Missing versus explicit JSON null

PowQL `->` intentionally scalarizes both a missing path and explicit JSON null to `Empty`.
That language semantic does not change in v0.13. `json_type()` is the supported distinction:

- missing path: typed `Empty`
- present JSON null: typed `Str("null")`
- present JSON string `"null"`: `json_type()` returns typed `Str("string")`

Per-cell typed results preserve those distinctions remotely. A fixed `Vec<TypeId>` without an
empty marker would not.

### D13.5: PowQL symmetric semantics are explicit in cached plans

PowQL aggregates over joins are symmetric by default. SQL aggregates stay raw SQL semantics.
Because both frontends share the canonical plan cache, SQL lowering must emit explicit `raw`
aggregate semantics in the AST and canonical form. Cache behavior must not depend on which
dialect warmed a structurally similar plan first.

Putting the dialect in the cache key is the fallback, not the recommendation. Explicit
semantics in the AST makes the plan self-describing and avoids duplicated cache entries where
the plans genuinely match.

## 5. Workstream A: expression and path indexes

### Deliverables

- Catalog v6 with `IndexKeySource::Column` and
  `IndexKeySource::Expression { index_id, canon_text, json_path }`.
- An active catalog write-version/capability field. Merely compiling a binary with catalog v6
  must not upgrade a v5 database on unrelated DDL, checkpoint, or recovery; the first
  expression-index creation activates and persists v6.
- A monotonic persisted `index_id` allocated by the catalog. New expression-index files use
  safe ID-based names rather than canonical expression text, so multiple paths on one JSON
  column cannot collide and path punctuation never reaches the filesystem. Existing
  column-index filenames remain readable through their legacy metadata until explicitly
  rebuilt.
- JSON-path-only validation and canonical identity in v0.13.
- Storage maintenance for insert, update, delete, upsert, rebuild, reopen, and unique checks.
- Scalar extracted values stored in the existing B-tree key space. Missing and JSON-null path
  values share a persisted `empty_rids` side set in the same expression-index lifecycle. They
  remain exempt from uniqueness and equality/range keys, but ordered scans append them for
  the required NULLS-LAST semantics without falling back to a table scan.
- Equality, inclusive/exclusive range, and ordered full-index scan plan nodes keyed by the
  expression signature rather than a stored column name.
- Runtime lowering to compiled `Filter(SeqScan)` when the speculative expression index is
  absent.
- `EXPLAIN` output that proves which expression index and scan direction execute.

### Correctness gate

- Equivalent path syntax canonicalizes to one index identity; different paths never collide.
- Equality and every range-bound shape return the same rows with the index enabled and absent.
- Reversed operands and compound bounds select the same index.
- Ascending and descending `order path limit K` return the same rows as forced sequential sort
  without a `Sort` node in the indexed plan. Null-heavy cases prove the persisted `empty_rids`
  side set is appended in stable NULLS-LAST order.
- Index maintenance survives update, delete, upsert, restart, rebuild, and WAL replay.
- Unique path indexes reject duplicate non-empty extracted scalar values.
- Inline and spilled JSON documents behave identically.
- Creating a path index fails atomically if any existing extracted value is an object/array.
  After creation, an insert/update/upsert that changes an indexed path to an object/array fails
  the statement atomically and leaves the row and index unchanged. Missing/null remain valid
  through `empty_rids`; missing/null to scalar and scalar to missing/null transitions update both
  structures. WAL replay, rebuild, rollback, and scalar-to-object failure cases are tested.
- Old binaries reject catalog v6 rather than misreading it.
- Drop, reopen, backup/restore, and rebuild address expression indexes by persisted `index_id`,
  never by recomputing a filename from expression text.

### Performance gate

- Rebuild the document-filter benchmark on the pinned 18,579-version reference dataset and
  retain the inherited
  under-5ms indexed-filter target on the reference benchmark runner. If the former 77,519-row
  scale is useful, preserve it as an explicitly synthetic document-row benchmark; 77,519 was
  the deleted EAV extraction-row count, not the reference document count.
- `order path limit 20` is O(K plus seek/traversal), not O(N log K), as proven by plan shape and
  a scaling benchmark.
- Existing stored-column point/range/order index benchmarks show no statistically meaningful
  regression.

## 6. Workstream B: document-read and typed-result fast path

### Deliverables

- A projected-row storage primitive that fetches/reassembles only requested columns.
- Index point/range projection paths use that primitive instead of `Table::get()` followed by
  full-row decode and clone.
- Additive typed query/result frames for PowQL, SQL, parameterized queries, rows, and scalars.
- Exact binary encodings for Int, Float, Bool, Str, DateTime, Uuid, Bytes, Json, and Empty.
- Rust and TypeScript codecs with the same payload limits and malformed-frame defenses as the
  legacy protocol.
- Direct PJ1-to-JS decoding in the TypeScript client.
- `queryNative()` public API and compatibility behavior for `queryTyped()`.
- External validation adoption so the benchmark exercises the new path rather than legacy
  strings. The external adapter and identifying workload details remain outside this repo.

### Correctness gate

- Projecting `.id` from a row with a large spilled document does not fetch that document's
  overflow chain.
- Projecting one JSON column from a wide row decodes only that column, inline and spilled.
- The typed document path performs zero server `pj1_to_text()` calls.
- For JSON values within JavaScript's safe numeric range, PJ1 decoding produces the same JS
  value as canonical JSON parsing for nested objects, arrays, Unicode, and null. PJ1 integers
  outside the safe range decode to `bigint`; floats decode to `number`. The JS value view does
  not claim to preserve the PJ1 `1` versus `1.0` tag distinction, but an optional raw-PJ1 cell
  view preserves exact canonical bytes for callers that need storage-level identity.
- Empty, literal string `"null"`, explicit JSON null through `json_type()`, empty string, zero,
  false, raw Bytes, DateTime, and Uuid round-trip without ambiguity or loss.
- Typed scalar results receive the same coverage as typed rows.
- Mixed-type JSON-path projection cells preserve each actual type.
- Legacy `0x07` row results remain byte-for-byte compatible.
- Old client/new server and new client/old server compatibility cases fail or fall back
  predictably, never by silently decoding a typed frame as text.

### Performance gate

Before native-wire implementation, check in a warm-cache legacy benchmark artifact for
identical indexed point reads of a typed row and a roughly 2.5KB document row over TCP. Record
p50, p95, CPU time, exact encoded bytes sent, and allocation count where the pinned harness can
measure it. The artifact identifies unavailable counters instead of inferring them.

After the native frames exist, run the same fixture and harness through the native path and
check in a second artifact. The release comparison is between those two named artifacts; Phase
0 does not pretend to measure a frame that has not been implemented.

Release target on the pinned reference environment captured in Phase 0:

- document p95 no more than 1.5x the equivalent typed-row p95;
- at least an 80 percent p50 reduction from the captured legacy document-read baseline;
- no server PJ1 text serialization on the typed path;
- legacy string behavior remains correct, with its conversion cost reported honestly.

About 2ms p50 remains the expected target when the pinned environment reproduces the reported
roughly 24ms baseline. If it does not, the captured reduction and typed-row ratio are the
authoritative release gates rather than an absolute number from a different run.

## 7. Workstream C: concurrent autocommit reads

### Design

Replace the single-permit semaphore with an async reader/writer admission gate.

- Healthy autocommit reads take a shared admission guard, then `RwLock::read` on the engine.
- Autocommit writes and `begin` take an exclusive admission guard, then the engine write lock.
  An explicit transaction retains its exclusive admission guard across statements until commit,
  rollback, disconnect cleanup, or cancellation.
- Admission is therefore atomic with respect to transaction visibility. There is no separate
  "is a transaction open?" check that can race with `begin` between the check and engine lock.
- If readonly execution returns `ReadonlyNeedsWrite`, release both shared guards, acquire the
  exclusive admission guard, and retry through the existing write/escalation path. Dirty
  materialized views are the primary case.
- All paths acquire admission before the engine lock. This fixed lock order is a tested
  invariant and prevents escalation deadlocks.
- PowQL, SQL, and parameterized query frames share one routing implementation.

This is a server routing change, not a new MVCC model. The engine's existing shared read lock
already gives query-level consistency: a read sees the state before or after a writer, never a
partially applied write.

### Correctness gate

- Real TCP tests prove at least two healthy autocommit reads overlap under shared admission
  without waiting for exclusive admission.
- A held explicit transaction still blocks another connection's read and preserves rollback
  visibility.
- A forced former-race interleaving proves `begin` cannot slip between read admission and the
  engine read lock; the read either enters first or waits behind the full transaction.
- Autocommit writes and overlapping `begin` retain the bounded wait and metrics behavior from
  v0.10/v0.11.
- A read concurrent with a write observes a complete before or after state, never partial rows.
- Dirty-view escalation releases both shared guards before waiting for exclusive admission and
  cannot deadlock.
- Query timeout and disconnect cancellation release the read lock promptly.
- Pipelined responses and group-commit behavior remain correct.

### Performance gate

Check in a TCP benchmark with 1, 2, 5, and 10 clients issuing a scan large enough to overlap.
Record aggregate throughput and p50/p95 latency. All clients share one start barrier and only
completions inside the common measurement window count toward throughput, so drain time cannot
bias larger client tiers.

- Ten healthy read connections must not show roughly 10x single-query latency.
- The default reference-machine gate is at least 5x one-client throughput at ten clients. Phase
  0 may replace that number before implementation only with checked-in evidence that CPU or
  storage saturates earlier and an explicit threshold at or above 80 percent of the measured
  saturation ceiling.
- One-client latency must not regress more than 5 percent.

The scaling ratio is primary; absolute latency depends on the machine and query shape.

## 8. Workstream D: expression-valued aggregate, group, and order

### Deliverables

- Replace field-name-only order, group, and aggregate inners with expression-valued forms in
  AST and plan nodes.
- Keep specialized stored-field arms or fast-path detection so existing hot paths do not lose
  performance.
- Support JSON paths in `sum`, `avg`, `count`, `min`, `max`, `group`, `having`, `order`, window
  order/partition positions included in the release, and qualified joined expressions.
- Reuse the same canonical expression identity used by expression indexes.
- Use ordered path indexes for compatible sort shapes; otherwise retain bounded top-K sorting.

### Correctness gate

- `sum/avg/count/min/max(.data->"x")` cover int, float, mixed numeric, missing, and JSON null.
- Import the actual anonymous grouping query/path into a checked-in fixture; it returns four
  verified group totals/counts of 529/547/528/535, totaling 2,139.
- Path group projection and HAVING aliases work.
- `order .data->"score" asc/desc` covers multi-key order, limit, offset, and the required
  NULLS-LAST behavior for missing and explicit JSON null.
- Filters exclude missing and explicit JSON null, while grouping folds both into the same null
  group, matching the reference relational baseline.
- Qualified joined paths work in group keys and aggregate arguments.
- Canonical object/array equality/order uses PJ1 Eq/Hash/Ord where those value shapes are valid.
- Indexed and forced-sequential execution return identical rows.
- Replace permissive "success or error" JSON-path tests with exact success results for supported
  positions and exact targeted errors for unsupported positions.

### Performance gate

- Stored-column aggregate/group/order benchmarks remain within 5 percent of the Phase 0
  pre-v0.13 baseline.
- The inherited 37ms comparison covers the old join/EAV shape, not a
  current native-path baseline. Capture the pre-v0.13 app-side-over-path baseline in Phase 0,
  then build the grouped raw-byte fast path only if the general expression implementation
  misses the resulting target. Measure first.

## 9. Workstream E: symmetric PowQL aggregates

### Semantics

For a PowQL aggregate whose argument has source alias A, aggregate distinct
`(group, rid_A)` contributions so fan-out cannot inflate the value. Deduplication is by source
RID, never by value.

- `count(*)` stays raw joined-row count.
- `sum(raw a.balance)` and analogous forms opt out.
- Min/Max skip the dedup set because duplicates cannot change their result.
- SQL lowering emits raw aggregate semantics explicitly.
- A symmetric aggregate expression must resolve to exactly one source provenance. Expressions
  such as `sum(a.x + 1)` are valid and use A's RID. Constants, ambiguous unqualified fields, and
  multi-source expressions such as `sum(a.x + o.y)` require explicit `raw` or fail planning with
  a targeted provenance error; PowDB never guesses which RID should deduplicate them.

### Implementation requirements

- Carry hidden row provenance through alias scans, hash joins, nested-loop joins, outer joins,
  projections needed by grouping, and multi-join plans.
- Charge per-aggregate dedup sets to the existing query memory budget.
- Allow unique-index/cardinality proof to elide dedup only as an optimization with identical
  results.

### Correctness gate

- The approved wedge fixture returns true `avg(a.balance) = 20.0` in PowQL and raw
  `avg(raw a.balance) = 15.0`.
- Two distinct source rows with the same value both contribute.
- Sum, count, and avg are correct across hash, nested-loop, left/right outer, and multi-join
  plans.
- Min/Max match raw results without allocating a dedup set.
- SQL returns 15.0 regardless of whether PowQL or SQL warmed the plan cache first.
- The raw modifier changes the canonical plan shape and survives plan-cache substitution.

## 10. Workstream F: SQL JSON arrows

### Deliverables

- Longest-token SQL lexing for `->>` before `->`.
- Postfix path parsing for object keys and array indexes.
- Lowering into the same PowQL `JsonPath` AST used by native queries.
- `->>` returns text for scalar, object, and array values. Object/array values use canonical
  JSON text.
- Projection, filter, aggregate, group, order, qualified references, and comparison parameters.
- SQL `CREATE INDEX` lowering to the native expression-index representation where supported.

### Correctness gate

- Lexer tests distinguish `->>`, `->`, subtraction, negative numbers, and comparison operators.
- The SQL arrow result matrix is fixed as follows:

  | Input path value | SQL `->` | SQL `->>` |
  |---|---|---|
  | string | scalar `Str` contents | `Str` contents |
  | integer/float | scalar `Int`/`Float` | decimal `Str` |
  | bool | scalar `Bool` | `"true"`/`"false"` `Str` |
  | object/array | `Json` subdocument | canonical JSON `Str` |
  | explicit JSON null | `Empty` | `Empty` |
  | missing | `Empty` | `Empty` |

- JSON-to-text cast support is added for object/array values; the current `CastType::Str` path
  returning `Empty` for `Value::Json` is not reused unchanged.
- Equivalent SQL/PowQL queries share cached plans only when their semantics are explicit and
  identical.
- `docs/SQL.md` documents the intentional divergence: PowDB SQL `->` inherits PowQL
  scalarization, while PostgreSQL generally preserves JSON values and distinguishes JSON null
  from SQL NULL for `->`.

## 11. Workstream G: compound-ON planning and bounded nested loops

### Deliverables

- Split conjunctions in `ON` predicates and extract an equi-key even when residual predicates
  are present.
- Hash on the equi-key, then evaluate residual predicates only within matching buckets.
- Preserve correct unmatched-row behavior for outer joins.
- Expose the selected join strategy in `EXPLAIN`.
- For a pure non-equi join with no extractable key, estimate `left_rows * right_rows` before
  execution. Reject above a documented `MAX_NESTED_LOOP_PAIRS` unless an explicit opt-in is
  added later. Do not rely on output row count because the expensive case can produce few rows.
- Keep the folded-in cooperative cancellation checks in every join loop as a last-resort bound.

The initial `MAX_NESTED_LOOP_PAIRS` value must be chosen from a scaling benchmark, not guessed
in the parser. It is a runtime safety limit because row counts are catalog/runtime facts and
the planner remains pure.

### Correctness and safety gate

- `a.id = b.a_id and residual` uses hash plus residual filtering.
- Swapped equality orientation and conjunction order select the same strategy.
- Inner and left/right outer residual semantics match forced nested-loop results on small data.
- Import the exact anonymous compound-ON query, minimal schema/cardinalities, and expected result
  into a checked-in regression fixture. It finishes within the normal
  query budget without needing the timeout.
- Large pure non-equi joins fail before entering an unbounded pair loop with a targeted error
  that names the pair limit and remediation.
- Small non-equi joins remain supported.
- Timeout and disconnect still stop any allowed nested loop and release all locks/permits.

## 12. Workstream H: targeted unsupported-path errors

Once expression-valued keys land, audit every remaining `JsonPath` position. Any unsupported
position must fail during parse/plan validation with:

- the construct name;
- the unsupported position;
- whether support is planned or intentionally excluded;
- a usable alternative when one exists.

Likely remaining cases include JSON mutation/set, arbitrary non-path expression indexes,
non-scalar unique path-index values, and any window path positions explicitly excluded from
v0.13.

The current `unexpected trailing token ... '->'` is not an acceptable v0.13 error. Tests assert
the error class and stable key wording, then issue a normal query to prove the server remains
healthy.

## 13. Sequencing and parallel lanes

### Phase 0: freeze the baseline

- Do not publish v0.12.1. Preserve the current cancellation work, finish disconnect signaling,
  and make timeout, disconnect, and prompt gate/lock release the first v0.13 verification gate.
- Pin the external validation snapshot, recording 9,270 parent records and 18,579 version
  records outside the repository so the reference workload cannot drift silently.
- Import the compound-ON repro and path-group expected rows into stable PowDB regression
  fixtures.
- Capture the missing legacy document-read and 1/2/5/10-client benchmark artifacts. Each
  machine-readable artifact records the commit and dirty-tree fingerprint, server/package
  version, OS/architecture, Rust version, fixture/query fingerprint, repetition metadata,
  exact response bytes, and raw samples or sufficient distributions.
- Record the v0.12.0 release plus folded cancellation changes as the v0.13 starting baseline,
  including plan shapes and the full benchmark suite. If shared-tree edits have already begun,
  reproduce the baseline from an isolated archive or prove that the measured legacy path is
  byte-identical; do not label a feature-modified path as the starting baseline.

### Phase 1: lock shared representations

Two short design spikes land first because they affect several lanes:

1. Expression-valued keys plus canonical expression/index identity.
2. Typed binary cells plus projected-row storage and the TypeScript native decoder.

These produce format fixtures before production implementation. Catalog v6 and typed wire
frames are additive one-way doors and receive adversarial review.

### Phase 2: parallel implementation

- Lane A: catalog v6, expression-index maintenance, filter/range/order scans.
- Lane B: projected-row storage, typed protocol, TS codec/client, document-read benchmark.
- Lane C: reader/writer admission gate and TCP concurrency tests.
- Lane D: expression-valued group/order/aggregate AST and execution.
- Lane E: compound-ON hash extraction and nested-loop pair bound.

Shared AST/plan files are owned by Lane D until the expression representation lands. Other
lanes consume that commit rather than editing the same files concurrently.

### Phase 3: dependent language work

## 15. Explicit non-goals

- MVCC, snapshot isolation across independent writer transactions, or multiple concurrent
  writers.
- General arbitrary expression indexes beyond JSON paths.
- GIN/containment indexes, JSON mutation operators, or JSON schema validation.
- Postgres/MySQL wire compatibility.
- Changing legacy `query()` string results or legacy `ResultRows` frames.
- Direct `->` distinction between missing and JSON null; `json_type()` is the supported surface.
- General join reordering or a cost-based optimizer. v0.13 extracts obvious equi-keys and bounds
  the unsafe fallback while preserving PowDB's pure planner model.
- Two-phase aggregate pushdown unless profiling after correctness shows it is needed.
- Compression or chunk-aligned PJ1 reads.

## 16. Risks and mitigations

- Typed wire grows into a protocol redesign. Keep it additive and opt-in, preserve legacy
  frames exactly, fuzz both decoders, and use golden cross-language fixtures.
- PJ1 moves to the client. The client decoder must validate bounds/depth and share canonical
  fixtures with Rust; malformed binary JSON is a protocol error, never partial data.
- Expression indexes touch persistent catalog and write maintenance. Land format/reopen/WAL
  tests before planner use and retain sequential fallback until all lifecycle paths pass.
- Concurrent reads can expose hidden interior mutation. Keep mutable view refresh/escalation on
  the writer path, audit shared caches for narrow synchronization, and run race-heavy soak tests.
- Symmetric provenance increases row width and memory. Keep it hidden, budget dedup sets, and
  measure multi-join workloads before enabling unique-proof elision.
- Expression-valued AST work can regress stored-field fast paths. Preserve specialized
  detection and make the existing benchmark suite a per-commit gate for that lane.
- Scope pressure can create a half-release. Tier 1 plus the private integration gate define the
  minimum coherent release; do not market v0.13 as the read release if those gates miss.
