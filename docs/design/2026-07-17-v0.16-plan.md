# v0.16 Plan: Honest and Correct

Date: 2026-07-17. Status: approved, in build.

Two workstreams: one correctness fix that requires an index format change, and a
positioning pass that aligns the public story with the engine's validated
strengths. Plus two recorded decisions that close open roadmap questions.

## Workstream 1: NUL-safe composite index keys

### Problem

Non-unique column indexes encode a string key as raw value bytes, a single 0x00
terminator, and the 8-byte rid. A value containing an embedded NUL (for
example "A\0") produces key bytes that can interleave in sort order with the
keys of a different value ("A"), because the terminator of one aligns against
content bytes of the other. Consequences, both shipping today:

- `lookup_prefix` (and therefore indexed equality, and index-driven deletes)
  can return or touch rows belonging to a different value: wrong rows.
- Per-index distinct statistics miscount for such values (documented
  limitation in v0.15).

### Fix

Order-preserving escape encoding for string values inside composite keys:
every 0x00 content byte is written as the pair 0x00 0xFF, and the value is
terminated by the pair 0x00 0x00. The two-byte terminator is what makes the
encoding prefix-free (a bare 0x00 terminator would leave enc("A") a byte
prefix of enc("A\0")); terminator 0x00 0x00 sorts below continuation
0x00 0xFF, so lexicographic value order is preserved and every value's key
range is disjoint. Bounded overhead: worst case 2x for a value that is all
NUL bytes.

### Migration: never silently serve an old index

The escaped encoding is a new non-unique index format version. On open, a
non-unique string-keyed index in the old format is rebuilt from the heap
automatically (the same machinery crash recovery already uses) and saved in
the new format. There is no mode that keeps reading old-format keys: a
correctness fix that depends on the operator knowing to rebuild is not a fix.
Unique indexes and expression indexes are unaffected (they never used the
composite string encoding).

### Acceptance

- The three-key repro ("A" rid 5, "A\0" rid 3, "A" rid 7) returns exactly the
  right rows for equality on each value, through index and seqscan alike.
- Distinct statistics exact for embedded-NUL values; the v0.15 documented
  limitation and its pinned test are replaced by exact assertions.
- An old-format index directory opened by the new binary is rebuilt on open
  and serves correct rows; a twin parity battery covers mixed NUL/plain data
  including mutations.

## Workstream 2: positioning

The engine's benchmark record is consistent: single-request query cost is
competitive to winning, and multi-client concurrent serving amplifies through
the write-admission gate. The public story should say what the engine is for
in exactly those terms:

- README leads with the fit list: single-writer embedded app state, local
  agent and tool memory, read-only edge snapshot serving, per-tenant
  process-isolated databases, CI and test databases, bulk ingest plus
  read-heavy internal tools. And the refusal boundary, stated plainly: for
  many concurrent clients over one shared read-write database, use Postgres.
- A concurrency decomposition document under docs/benchmarks/ publishing the
  single-request versus concurrency-10 behavior with a reproducible script,
  in the same honest register as docs/powdb-vs-sqlite.md.
- A flagship runnable example, examples/edge-snapshot-serving/: backup on a
  writer, restore, serve the directory with N read-only server processes,
  refresh by restoring beside and swapping. This is the blessed read-scaling
  pattern.
- Transaction guidance in the language reference: an explicit transaction
  holds the whole admission gate, blocking all readers for its lifetime; keep
  transactions short and prefer autocommit statements on read-mostly paths
  (autocommit releases admission before the fsync wait).

## Decisions recorded

1. **Agent memory is local-first and single-process; the live
   apply-while-serving sync lane is closed.** A live applier is a writer, and
   a writer takes the entire admission gate; live tailing while serving would
   reintroduce the exact write-blocks-reads behavior this engine's design
   accepts as a permanent boundary (no MVCC). Freshness is delivered by
   snapshot refresh (seconds), not by streaming. The sync crate is retained
   deliberately: it is the substrate for WAL shipping, incremental backup,
   and snapshot refresh, and continues to be hardened for those uses.
2. **Concurrent-read amplification: diagnose next cycle, scoped.** The open
   question that matters is whether read amplification appears in --readonly
   serving (the kept niche), not in shared read-write serving (the refused
   niche). Profiling lands next cycle; a fix is committed only if the kept
   niche is affected.

## Non-goals

- MVCC, multi-writer, or any admission-gate redesign (permanent boundary).
- Live shared-directory replica tailing (decision 1).
- Online schema change, disk-spill sorts, Windows/musl targets (unchanged).
