# v0.5.0 Design Lock — Format, Dialect, BufferPool

**Date:** 2026-06-16

This locks the three v0.5.0 foundation decisions that must be stable before
implementation work starts on transactions, on-disk format versioning, SQL, or
cleanup. It is intentionally narrow: these decisions are the permanent product
and format boundaries for the next implementation lanes, not a full roadmap.

- Roadmap/worklist: tracked in the internal planning docs.

  `catalog.rs`, `disk.rs`, `btree.rs`, and `buffer.rs`.

  `canonicalize.rs`, `planner.rs`, and executor entry points.
- Operational triage: tracked internally.

## D-1: Heap-file versioning uses a page-0 superblock

**Decision:** v0.5.0 heap files get a dedicated page-0 superblock. Data pages
move to page IDs `>= 1`. The superblock is a `PageType::Meta` page containing a
heap-file magic, format version, feature flags, page size, and offsets needed for
future readers. Unknown major versions and incompatible feature flags must fail
open loudly before any row/page decode.

**Why:**

- The existing page format has `PageType::Meta = 5`, but heap page 0 is live data
today. The worklist correctly marks heap-file versioning as the special case
where “no version means v1” is not enough.
- A sentinel embedded into a data page would preserve page 0 as data but makes
all page readers carry a special-case and risks confusing mmap scan fast paths.
A superblock gives one front-door compatibility check before any page iteration.
- Future features in the roadmap (nested values, search/vector/document indexes,
time-travel-adjacent undo data) need a place to advertise format capabilities.
A page-0 superblock is the least surprising DB-file convention.

**Compatibility rule:**

- Existing heap files without a superblock are treated as **legacy heap v1**.
- v0.5.0 must provide an explicit migration/open path that either:
  1. rewrites legacy heaps into superblock format during a controlled migration,
     or
  2. opens legacy heaps read/write through a compatibility shim while new heaps
     are created in v2 format.
- Do not silently reinterpret an unknown page-0 image as a new heap. If page 0
  claims `Meta` but fails magic/version validation, open fails.

**Implementation tasks:**

- Add constants and validation helpers for heap-file magic/version/flags.
- Teach `HeapFile::create` to allocate/write the superblock first, then allocate
  data pages from page 1.
- Teach `HeapFile::open` to detect legacy v1 versus superblock v2 and reject
  unknown versions.
- Audit every page-id assumption in heap, WAL replay, backup/incremental backup,
  table/index rebuild, and tests.
- Add corrupt/unknown-version tests for heap superblock, page header version,
  row encoding version, and WAL file magic.

**Rejected:** sentinel row/slot in page 0. It preserves old page numbering
but turns a file-level invariant into a data-page convention, increasing the
chance of silent misdecode.

## D-2: Dialect selection is explicit per connection

**Decision:** SQL/PowQL dialect is a connection-level setting, defaulting to
PowQL for the existing binary protocol and embedded API. The server may also
accept an explicit dialect flag in a future handshake or config field. Statement
sniffing is allowed only as a convenience fallback when the connection is in an
`auto` mode; it must never be the only way to select dialect.

**Why:**

- Existing clients and embedded users call `execute_powql` and must keep current
semantics by default.
- SQL has keywords and expression shapes that can overlap with future PowQL
syntax. Pure sniffing creates hard-to-debug ambiguity and can break new PowQL
features later.
- A connection-level setting lets plan-cache canonicalization and error messages
carry the source dialect without re-planning or changing the executor. Both
frontends still target the existing `Statement`/`Expr` AST and planner.

**API shape:**

- Embedded Rust:
  - keep `execute_powql(&str)` unchanged;
  - add `execute_sql(&str)`;
  - optionally add `execute_with_dialect(Dialect, &str)`.
- Server/client protocol:
  - preserve existing query message behavior as PowQL;
  - add a backward-compatible dialect field/message or connection option before
    advertising SQL support as stable;
  - keep parameter binding token-level and dialect-aware.
- CLI:
  - default remains PowQL;
  - add `--dialect powql|sql|auto` and/or REPL command for dialect.

**Plan-cache rule:** equivalent SQL and PowQL must lower to equivalent AST/plan
shapes, but the cache key should include enough frontend/canonicalization context
that SQL literal normalization cannot corrupt PowQL semantics or vice versa.
Parity tests must prove identical results and plan intent, not rely on raw query
text identity.

**Rejected:** separate SQL port as the primary v0.5.0 mechanism. It may be useful
for a future PostgreSQL-wire-compatible surface, but it fragments local embedded
and binary-client behavior before the SQL frontend is stable.

## D-3: Delete unused BufferPool unless replacement lands

**Decision:** the v0.5.0 cleanup lane deletes the exported `BufferPool`
module and its dedicated tests unless the team first lands a measured
replacement of the current heap hot-page/dirty-buffer cache. The default cleanup
task is deletion, not integration.

**Why:**

- `crates/storage/src/buffer.rs` implements a separate clock-sweep buffer pool,
  but repository usage is limited to its own tests (`crates/storage/tests/buffer_pool.rs`).
- The active heap path already has load-bearing caching in `HeapFile`: one hot
  page plus a deferred dirty-page buffer, with explicit scan/mmap flush
  invariants.
- Shipping two cache implementations makes correctness review harder exactly as
  the transaction and format lanes touch dirty-page, WAL, rollback, mmap, and
  backup behavior.

**Deletion tasks:**

- Remove `pub mod buffer` and `crates/storage/src/buffer.rs`.
- Remove or rewrite `crates/storage/tests/buffer_pool.rs` so tests cover the
  active `HeapFile` cache invariants instead.
- Confirm no public crate examples or docs advertise `BufferPool`.
- Run storage/query tests and benchmark smoke checks after deletion.

**Replacement escape hatch:** keep `BufferPool` only if a branch first proves all
of the following in one focused PR:

1. it replaces the active `HeapFile` hot-page/dirty-buffer path rather than
   existing beside it;
2. it preserves mmap invalidation, WAL replay idempotence, dirty flush, and
   rollback requirements;
3. it beats or matches the current cache on representative insert/update/delete
   and scan workloads.

**Rejected:** keeping both caches. The extra abstraction cost is paid in every
review of the v0.5.0 storage work, while no current production path uses the
clock-sweep implementation.

## Locked sequencing constraints

1. Format work (`FMT`) must land before nested values or any new persisted
   structure.
2. Transaction work (`TXN`) and format work both touch heap/WAL/catalog replay;
   merge them through a single integration branch or serialize their landing.
3. SQL frontend work can proceed in parallel only while it targets existing AST
   surfaces and does not change executor semantics.
4. BufferPool deletion should be an early cleanup PR because it reduces the
   transaction/format review surface.
