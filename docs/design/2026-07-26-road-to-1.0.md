# Road to 1.0

**Status:** proposed, pending decisions in [Open questions](#open-questions)
**Date:** 2026-07-26
**Baseline:** v0.20.0
**Horizon:** 12 releases (0.21.0 through 1.0.0)

## Thesis

PowDB v0.20.0 is a strong 0.x storage engine wrapped in a database that is not
yet safe to build an application on. The gap to 1.0 is not one large feature. It
is four things that must happen in a specific order:

1. The defect classes still shipping today become typed errors.
2. The machinery that would have caught them exists **before** any format change.
3. The on-disk format is bumped once, deliberately, with future sections
   reserved.
4. Only then do concurrency and MVCC proceed, so they can be judged by evidence
   rather than by feel.

This ordering is not the obvious one, and it is not the one originally proposed.
Both adversarial reviews of the first draft returned **RESEQUENCE**. See
[Why this order](#why-this-order).

## Where we actually are

**6.5 / 10** as a general-purpose single-node database. Roughly **8 / 10** as a
0.x specialist engine: the WAL, group commit, crash recovery, page CRCs, lazy
format activation, and the honesty of `docs/STABILITY.md` are genuinely good.

What holds it below 9, all verified in code:

## Why this order

The first draft sequenced types → concurrency → MVCC, with assurance work spread
across all three. Two independent adversarial reviews rejected it. The
substantive objections, and what changed:

**Types before test machinery is backwards.** A temporal and decimal row format
is exactly the kind of change whose bugs are invisible to hand-written tests, and
it is the change that is most expensive to get wrong because users migrate onto
it. The differential oracle, the access-path equivalence runner, and cross-version
compatibility CI now land in 0.22.0, **before** the first format change in
0.23.0, and are hard gates on it rather than soft ones.

**Concurrency and MVCC were two workstreams building the same thing twice.** The
drafts had a committed-overlay snapshot reader, a `MappedRegion` abstraction, and
a productionized `enable_mmap` path, all of which the buffer pool plus row
visibility supersede. They are merged into one workstream and the duplicated
mechanisms are deleted rather than kept.

**Five migrations became two.** Catalog v8 is now defined **once** as a
length-tagged container with every future section reserved and zero-written
(column type params, primary key, `mvcc_enabled`, `next_tx_id` high-water), so
v8 is the last catalog version before 1.0.

**The cheap high-severity fixes were gated behind four releases of
infrastructure.** The findings above are in the tree now. They ship first, in
0.21.0, depending on nothing.

## The releases

| Release | Name | Goal |
|---|---|---|
| 0.21.0 | Correct or Error | Every known silent-wrong-answer and client-reachable availability bug is fixed or a typed error |
| 0.22.0 | Provable | Build the machines that would have caught them, plus wire version negotiation, before any format change |
| 0.23.0 | Catalog v8 and Real Time | One migration that never repeats: v8 as a reserved container, plus real date and time types |
| 0.24.0 | Exact Numbers | Money arithmetic is exact; no schema silently becomes binary float |
| 0.25.0 | Keys and Migrations | Primary keys, and a schema that can evolve after it ships |
| 0.26.0 | Query Surface and Result Delivery | Two-predicate queries use an index, large results stream, the ORM shape compiles |
| 0.27.0 | Buffer Pool and Read Scaling | One shared latched page cache replaces three ad-hoc mechanisms; reads scale with cores; `open` stops being O(database) |
| 0.28.0 | Transactions That Are Actually Transactions | ROLLBACK is O(transaction), the WAL is bounded on a running server, recovery has a real undo pass |
| 0.29.0 | MVCC Engine | Row-level visibility exists, is correct, and is proven, with the admission model deliberately unchanged |
| 0.30.0 | Snapshot Readers On | An open transaction stops excluding readers; server and embedded run the same named model |
| 0.31.0 | Operate It | Back up, verify, salvage, diagnose, and audit a live database without stopping the world |
| 1.0.0 | Freeze | Every guarantee written down, versioned, tested; the API stops moving |

Full per-release work items, sizes, and exit criteria are in the companion
plan; every exit criterion is objectively checkable (a test exists, a benchmark
number, a format version, a documented guarantee), never "improved".

### 0.21.0 in detail

Ships first because it depends on nothing.

- Join-scope unqualified column resolution, with a hard ambiguity error when two
  aliases expose the same name
- DDL inside an explicit transaction becomes a typed error (a refusal, not
  transactional DDL; the real thing is deferred to a decision below)
- Bounded transaction dirty set with a typed `TransactionTooLarge`
- Parse failures no longer acquire an admission permit
- Aggregates over non-numeric values and integer overflow become typed errors on
  all three aggregate paths, which must agree or the answer depends on which
  path fired
- Unsupported and undefined arithmetic stops evaluating to NULL, with checked
  arithmetic in `date_add`
- CI hygiene: assert every test filter matches at least one test, so a job
  cannot silently under-run again

## Format migrations

**Four format version bumps across twelve releases, collapsed into two
user-visible migration events, zero of which require operator action.**

**Event 1, v0.23.0:** catalog 7 → 8, BTREE 3 → 4. The catalog bump is lazily
activated exactly like v6 and v7, so a database that never declares a date,
time, decimal, primary key, composite index, or MVCC feature stays byte-identical
and keeps opening on 0.22.0 and earlier. The btree bump carries a one-time
rebuild at open scoped only to temporal and decimal columns.

**Event 2, v0.29.0:** the row format gains visibility information, activated only
when MVCC is enabled, with a downgrade tool.

## What 1.0 requires

Each condition names the release that closes it.

- Wire protocol version negotiation, so a client/server mismatch is a typed error
  at connect (0.22.0)
- No silent wrong answers reachable from any supported query, proven by a
  differential oracle over full result sets and an access-path equivalence
  runner, not by hand-written tests (0.22.0, enforced continuously after)
- Real exact-numeric and temporal types: money that does not become binary
  float, a timestamp index that can be probed (0.23.0, 0.24.0)
- A schema that can evolve after it ships: defaults with backfill, required
  promotion, rename, truncate, `INSERT ... SELECT` (0.25.0)
- A downgrade story: backward-compatible readers plus supported export/import,
  observed against real released binaries rather than asserted by construction
  (0.25.0, 0.29.0)
- Result delivery that does not require the whole result set in memory, and
  composite indexes (0.26.0)
- ROLLBACK whose cost is O(transaction), and a WAL bounded on a running server
  (0.28.0)
- A named, tested isolation level that is a property of the engine rather than of
  a server-side semaphore, identical for server and embedded (0.30.0)
- Online backup: a recoverable copy taken without stopping every writer (0.31.0)
- Operability: verify, salvage, audit log, slow-query log, per-index usage
  counters, least privilege that does not grant DDL to the application tier,
  executable documentation with a generated limits page (0.31.0)
- A settled PowQL surface with a written deprecation path, and stable Rust and
  TypeScript APIs under normal SemVer (1.0.0)
- **Explicit written refusals** for what 1.0 deliberately excludes (foreign keys,
  CHECK, ATTACH, VACUUM, encryption at rest, multi-writer concurrency, index-only
  scans, paged B+trees), so absence is a documented decision rather than
  something a user discovers in production (1.0.0)

## Open questions

These need a decision before the releases they gate.

1. **MVCC scope.** Accept single-writer snapshot isolation as the 1.0 target,
   explicitly refusing multi-writer concurrency, write-write conflict detection,
   and a lock manager? The 0.27.0-0.30.0 sequence is sized against that answer.
   Multi-writer roughly doubles it and adds deadlock detection to a codebase that
   has never had a lock manager.
2. **Resident B+trees.** Every index is an in-memory `Vec<Node>` saved by
   whole-file rewrite, so total index size is bounded by RAM and every checkpoint
   touching an index rewrites its entire file. Plan is to measure and publish the
   ceiling and refuse paged indexes for 1.0. Accept the refusal, or add an XL
   paged-index sprint?
3. **The join-scope fix.** Implement the suffix match with an ambiguity error
   (compatible, keeps working queries working) or delete the offending loop
   (strict, minimal, turns an unknown number of existing tests and doc examples
   into hard errors)? The compatible variant is planned; the strict one is
   defensible given the project's correct-by-default value.
4. **Transactional DDL.** Build it in 0.28.0 on the undo log, or make the 0.21.0
   refusal permanent and documented?
5. **C ABI.** Ship `powdb-c` with a stable header as the single ABI for
   non-Rust/non-Node languages, or reposition embedded PowDB as a Rust and Node
   product? There is no `extern "C"` anywhere today, so the current positioning
   against SQLite implies a reach the product does not have.
6. **Float → Int coercion on insert** currently truncates silently, saturates out
   of range, and turns NaN into 0. Error, round with a documented rule, or keep
   and document?
7. **Bench as a required merge gate in 0.22.0.** It will block merges on
   performance for the first time. The same-instance control run is what makes it
   defensible, but it is a workflow change.
8. **Decimal precision of 38 digits** (i128 unscaled). Sufficient, or does a
   target workload need more, forcing variable-length representation and a
   different index-key encoding?
9. **Windows.** Full support at 0.31.0 (made cheap only because the 0.27.0 buffer
   pool deletes the ungated mmap sites), or a permanent documented refusal?
10. **Horizon.** Twelve releases is roughly 12-18 months for a small team. If
    that is too long, the honest lever is to pull 0.26.0 (query surface, the tier
    applications hit in week one) earlier and push MVCC later. The lever *not* to
    pull is compressing 0.22.0, since every later format and visibility change is
    judged by it.

## Method

This plan was produced by mapping five subsystems against the actual code
(transactions/durability, types/encoding, concurrency, testing/reliability,
capability gaps), designing each workstream independently, then subjecting the
result to an adversarial sequencing review and a completeness critic. Both
critics returned RESEQUENCE and both were adopted. Claims about current behavior
were spot-verified against the shipped v0.20.0 binary before being recorded here.
