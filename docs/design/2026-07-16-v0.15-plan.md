# v0.15 Plan: Per-Index Statistics for Conjunction Index Choice

Date: 2026-07-16. Status: approved, in build.

## Goal

v0.14's conjunction index selection picks the best index by a fixed tier
heuristic (unique eq > non-unique eq > range) with first-conjunct-wins ties.
Partner benchmarking quantified the failure shape: a conjunction whose
textually-first (or only) indexed conjunct is unselective (a boolean flag, a
few-distinct JSON path) drives the scan through that index, materializing a
large rid set plus a per-rid residual recheck, which is slower than the
seqscan it replaced. On the partner's S4-shaped workload (json-equality
conjunction, ~19K rows) this is the one remaining read scenario bound by
query cost rather than admission: ~198ms single-request where siblings run
5-8ms.

Fix: coarse per-index statistics (total entries, distinct keys) feeding the
existing chooser, so it ranks candidates by estimated rows per key instead of
build order within a tier.

Acceptance (external harness, same-day):

1. `explain` on the S4 shape picks the selective index even when the
   unselective conjunct comes first textually.
2. S4 single-request p50 drops an order of magnitude.
3. Full indexed-vs-unindexed parity battery stays green (21/21).

## Design

### Storage lane (powdb-storage)

`BTree` gains two in-memory counters, `total_entries: u64` and
`distinct_keys: u64`, plus O(1) accessor `BTree::stats() -> IndexStats`:

```rust
pub struct IndexStats {
    pub total_entries: u64,   // non-empty keys in the tree
    pub distinct_keys: u64,   // distinct logical keys (composite prefix for non-unique)
    pub empty_count: u64,     // v2 empty_rids side list length
}
```

- **No on-disk format change.** Counters are NOT persisted: `load` already
  deserializes every node, so both counters are computed during load with the
  same walk (distinct = key transitions along the leaf chain; non-unique
  trees compare the composite key's value prefix, i.e. bytes minus the
  trailing 8-byte rid). `BTREE_VERSION` stays 2; old binaries keep reading
  new files and vice versa.
- **Maintenance.** `total_entries` is exact: `insert`/`insert_int` learn to
  report whether the key was new (the replace branch already knows), deletes
  already return bool. `distinct_keys` is exact on unique trees (the same
  new-vs-replace signal). On non-unique trees the insert checks the
  neighboring composite key at the insertion point for a shared value prefix
  (adjacent by sort order); deletes check both neighbors. If the neighbor
  check proves fiddly in any path (e.g. `insert_duplicate`'s whole-tree
  rebuild fallback), that path may instead mark counters stale and recompute
  during the next `save_to`/checkpoint walk, which serializes every key
  anyway. Correctness bar: counters must never drift permanently; a stale
  counter heals at the next checkpoint or reload.
- **Rollback.** `discard_dirty` re-opens from disk; recomputation during load
  heals counters automatically. Audit that no discarded in-memory counter can
  be observed or persisted.
- **Empty values** stay excluded from both counters (they live in the
  `empty_rids` side list, reported separately as `empty_count`).
- **WAL: zero impact.** Index mutations are not WAL-logged; recovery rebuilds
  indexes from the heap, which rebuilds counters for free.
- Catalog accessor: `Catalog::index_stats(table, column) -> Option<IndexStats>`
  and the expression-index equivalent by `index_id`, both O(1) reads of the
  loaded tree's fields.

### Executor lane (powdb-query)

In `lower_conjunction_scan` (crates/query/src/executor/plan_exec.rs), replace
the tier-only ranking with an estimated-rows key:

- unique eq candidate: `est = 1` (no stats read needed)
- non-unique eq candidate (column or expression index):
  `est = total_entries / max(distinct_keys, 1)`; when the probe literal is
  the empty/missing sentinel, use `empty_count` instead
- range candidate: `est = total_entries` (range estimation is out of scope;
  tier ordering preserves v0.14 behavior when no eq candidate exists)

Rank by `(est, tier, build_order)`. The chooser only compares candidates
against each other, never against a seqscan (unchanged from v0.14); the
residual recheck guarantees a wrong estimate is a performance bug, never a
correctness bug. Stats are read per execution inside runtime lowering (the
plan cache stores pre-lowering plans, so a stale choice can never be cached),
which is why the reads must be O(1) field accesses.

`explain` appends stats tokens to chosen index-scan lines in
`format_plan_tree`, recomputed from the catalog:
`IndexScan table=T column=c key=... est_rows=3 entries=120 distinct=40`.
Annotation text must not contain scan-node names (`IndexScan`, `SeqScan`,
`ExprIndexScan`, `RangeScan`, `Filter`): several tests assert negative
`contains()` on those words.

### Tests

- Extend crates/query/tests/conjunction_index.rs in the existing style:
  - Shape inversion: skewed seed (50/50 boolean indexed, 50-distinct column
    indexed, few-distinct JSON path indexed); assert explain picks the
    selective driver even when the unselective conjunct is textually first,
    for both column and expression indexes.
  - Parity: the same skewed queries through the twin-engine
    indexed-vs-unindexed pattern, including mutations.
  - Stability: execute twice with explain between, proving the plan-cache
    hit path re-lowers with current stats.
- Storage unit tests: counter exactness through insert/replace/delete on
  unique and non-unique trees, composite-prefix distinct counting,
  empty-list exclusion, heal-on-reload, heal-after-rollback, counter
  behavior through `insert_duplicate`'s rebuild fallback.
- Update `column_index_and_path_index_are_both_honored`, which currently
  pins first-conjunct-wins tie order.

## Non-goals

- Skew-aware per-key estimates (bounded `lookup_prefix` probes): follow-up
  only if partner data proves skewed enough to mislead avg-rows-per-key.
- Choosing seqscan over an index (needs table cardinality; separable).
- Range-bound selectivity estimation.
- Persisting stats on disk, table-level statistics, or a cost model.
- Any change to the admission gate (the c10 serialization ceiling is a
  different lane; partner data confirms read-only/embedded sidesteps it).

## Risks

- Non-unique distinct maintenance is the subtle part; the checkpoint-walk
  recompute is the sanctioned escape hatch wherever incremental tracking is
  not provably exact.
- Behavior change for anyone relying on conjunct order to force a driver;
  the explain annotation is the mitigation.
- `entries/distinct` is average selectivity; heavy skew can still mislead
  (documented, accepted for v0.15).
