# v0.14 Plan: Conjunction Index Selection, Embedded Parity, Read-Only Snapshot Serving

Status: PROPOSED (design review pending)
Date: 2026-07-15
Prior art: docs/design/2026-07-14-v0.13-plan.md (shipped in v0.13.0)

## Motivation

Downstream production validation of v0.13 (a document-heavy CMS-style serving
workload benchmarked three ways against Postgres-backed stores) reached zero
app-side workaround code for the first time and closed every prior ask. Its
data now points at exactly three remaining gaps, in this order:

1. The planner uses an index only when a filter has exactly one predicate. The
   dominant real-world filter shape is a conjunction
   (`.model_id = $1 and .is_published = true and .data->ns->value = $2`),
   which executes as a sequential scan of the whole table (~29 ms over 19K
   rows) while the equivalent single-predicate path filter uses the v0.13
   expression index at ~3.2 ms. This one behavior is the dominant remaining
   cost in filter/count/sort serving shapes.
2. The engine's strongest deployment modes (embedded, read-only serving) lag
   the server: embedded results are lossy strings and cannot bind parameters,
   and there is no supported way to open a data dir read-only with no write
   gate at all.
3. The lossless null-vs-missing distinction shipped in v0.13 is only received
   by clients of the native typed API; the legacy string protocol (which
   existing ORM drivers speak) still collapses empty, string "null", and JSON
   null into the same bytes.

The positioning insight behind lanes 2 and 3: measured per-op reads are faster
than a Postgres network round trip, writes never corrupt and never fail under
contention (FIFO admission is correct semantics, not a limitation), and the
whole engine is one binary and one directory. The single-writer gate only
costs anything when many concurrent clients funnel through one server
process; it disappears embedded and in read-only serving. Investment should
flow to the lanes the architecture already wins.

## Scorecard driving this plan

## Lane A: conjunction index selection with residual recheck (priority 1)

### Current behavior

The planner is catalog-pure and speculatively folds only two filter shapes
into index scans (`crates/query/src/planner.rs:136-156`):

- single equality (`try_extract_eq_index_key`, planner.rs:630) → `IndexScan`
  / `ExprIndexScan`
- single-column range or same-column BETWEEN pair
  (`try_extract_range_index_keys`, planner.rs:782) → `RangeScan` /
  `ExprRangeScan`

A top-level `and` conjunction matches neither extractor and falls through to
`Filter(SeqScan)`. The limitation is already documented as a future
optimization at planner.rs:123-125. Runtime lowering
(`lower_unindexed_scans`, `crates/query/src/executor/plan_exec.rs:6135`) is
the single catalog-aware choke point that resolves speculative index scans or
demotes them.

Three facts make this fix cheap:

- `Filter(IndexScan)` already executes correctly today via the general Filter
  arm (plan_exec.rs:984-1002): run the inner scan, recheck the predicate with
  `eval_predicate`. No new plan node and no new executor arm are required for
  correctness.
- The two shape extractors are catalog-free functions and can be reused from
  lowering.
- `explain` renders a `Filter(IndexScan)` tree naturally (plan_exec.rs:6537).

### Design

Implement selection in **runtime lowering**, not the planner, so the planner
stays pure and the choice is made with real catalog knowledge:

1. New arm in `lower_unindexed_scans` for `Filter { input: SeqScan, predicate }`
   where the predicate is a top-level `and` chain:
   - Flatten the conjunction.
   - Run each conjunct through the existing eq/range extractors to find
     candidate index scans; keep only candidates whose index actually exists
     (`Catalog::has_index` / `resolve_expression_index`).
   - Pick the winner by a zero-stats selectivity heuristic:
     unique-index equality > non-unique equality > range. Ties broken by a
     bounded probe (see Tradeoffs).
   - Rewrite to `Filter(remaining conjuncts)(chosen index scan)`. If no
     candidate resolves, keep today's `Filter(SeqScan)` byte-identical.
2. Mirror the same treatment for UPDATE/DELETE discovery scans (the planner
   folds those the same way at planner.rs:542-581).
3. **Compiled residual recheck fast path.** The general Filter path
   materializes the index-scan result before rechecking. Add a fast-path arm
   mirroring the compiled `Filter(SeqScan)` loop (plan_exec.rs:916) that
   sources rids from `index_lookup_all` / `range_rids` and applies the
   compiled residual predicate over raw row bytes. This is what turns the
   conjunction shape into single-digit milliseconds instead of merely
   "better".
4. **Explain reflects the executed plan.** Today explain formats the
   un-lowered plan; a speculative index scan renders even when execution will
   demote it (expression scans print `index_id=unresolved`, column scans
   print nothing at all about demotion). Run the same lowering before
   formatting so `explain` output is the plan that will actually execute.
   This is also the acceptance instrument for this lane.

### Semantics and safety

- Residual recheck preserves exact filter semantics: the index narrows the
  candidate set, the full conjunction re-evaluates on each fetched row.
  Cancellation checkpoints already exist in both scan paths.
- Missing/JSON-null keys are valid indexed values (NULLS-LAST, v0.13), so an
  equality conjunct on a path with missing keys is safe to drive the scan.
- Plan-cache interaction: cached canonical plans store the planner's shape;
  lowering runs per execution, so index create/drop between executions is
  picked up with no cache invalidation changes.

### Tradeoffs (flagged)

- **Probe cost on the hot path.** Lowering runs on every execution. A
  selectivity probe that calls `index_lookup_all(...).len()` per candidate
  adds real work to every query. Default to the ordinal heuristic (unique >
  eq > range, first match wins within a tier); probe only when two or more
  candidates land in the same tier, and consider capping the probe (e.g.
  compare bounded rid counts). If even that shows regression on the 20-bench
  suite, ship heuristic-only. There are no table statistics in the engine and
  this plan deliberately does not add any; a stats subsystem is a much larger
  commitment and nothing in the measured workloads needs it yet.
- **A wrong pick is only ever slower, never wrong.** The residual recheck
  makes selection a pure performance decision, which is what makes this lane
  safe to ship quickly.

### Acceptance

- `explain` on the three-conjunct shape above shows an index scan with a
  residual Filter instead of SeqScan.
- New bench workload (conjunction filter over 20K rows, one indexed path
  conjunct) lands within ~2x of the single-predicate index-scan time, from
  ~9x today.
- Existing 20-workload criterion suite shows no regression (Depot run).
- Full parity of query results on conjunction shapes with and without
  indexes present (property-style test comparing lowered vs unlowered
  execution).

## Lane B: embedded parity (typed results + parameters)

### What is already at parity (documentation gap, not code gap)

The Node addon executes PowQL text through the same
`Engine::execute_powql` as the server, so expression-index DDL, path
group/order/aggregate, transactions, and `explain` all already work embedded.
This must be stated in the addon README because downstream users currently
assume embedded lags the server on engine features.

### Real gaps (both in the result/transport layer)

1. **Typed lossless results.** `bindings/node` renders every cell through
   `Value::to_wire_string` (crates/storage/src/types.rs:95-115): bytes become
   `"<N bytes>"` (irrecoverable), JSON-null and SQL-null both become the
   string `"null"`, ints become decimal strings. Embedded today is exactly as
   lossy as the legacy wire.
2. **Parameterized queries.** The engine has
   `execute_powql_with_params`; the `powdb` facade and the addon expose no
   params method at all.

### Design

- Facade: add typed-result query methods on `powdb::Database` returning
  typed `Value` rows (the `TypeId` tagging logic already exists server-side
  in `encode_typed_value`, protocol.rs:805-826; share it).
- Addon: add `queryNative(powql)` / `querySqlNative(sql)` /
  `queryWithParams(powql, params[])` mapping `Value` to real JS types:
  Int → `bigint`, Float → `number`, Bool → `boolean`, Bytes → `Buffer`,
  Json → parsed value plus raw PJ1 `Uint8Array` (mirror the TS client's
  `WireValue` shape so both surfaces present the same union), Empty → tagged
  empty distinct from JSON null. Existing string-based `query()` stays
  byte-identical for compat.
- Keep the sync client contract untouched (it needs only `queryReadonly` +
  `applyRetainedUnits`, both present).

### Acceptance

- Addon test matrix covering all nine TypeIds round-tripping to JS, the
  null-vs-missing distinction, i64 beyond `Number.MAX_SAFE_INTEGER`, and
  param binding.
- README parity table: capability x {server, embedded} with explicit
  "identical engine" framing.

## Lane C: read-only snapshot serving (tier 1 of the replica story)

### Finding: nothing opens read-only today

Every "readonly" in the stack is per-connection RBAC or per-statement
admission inside a read-write process. The physical open path opens files
read-write, chmods the data dir, replays and **truncates** the WAL, and takes
an exclusive PID lock. Two-process access to one dir is unsafe by
construction (in-place page writes, intra-process-only mmap coherence, no
catalog reload).

### Design: bless "snapshot → serve read-only", explicitly not "apply while serving"

Tier 1 ships a genuinely read-only open for **quiescent** directories (a
restored backup or a checkpointed replica: both already guaranteed
WAL-clean by `restore`'s validating open):

1. `Catalog::open_read_only(dir)`: files opened read-only, no
   `set_permissions`, **refuse** a non-empty WAL with a clear error naming
   the fix (open read-write once, or restore a backup) rather than replaying.
2. `Engine::open_read_only`: no write lock taken; `DirLock` gains a shared
   reader mode so N read-only processes may coexist (still refusing a live
   writer, and a writer refuses live readers: cross-process torn reads stay
   impossible rather than "unlikely").
3. Statement policy: `ReadonlyNeedsWrite` becomes a terminal, well-named
   error (`readonly mode: statement requires a writer`); no escalation path
   exists. Materialized-view refresh must happen before snapshotting; the
   error message says so.
4. Server: `--readonly` flag / `POWDB_READONLY=1`. Readers never touch the
   writer side of the admission gate, so concurrent read scaling has no
   write-gate serialization at all in this mode.
5. Embedded: `Database.openReadOnly(dir)` on the addon; this plus Lane B is
   what makes an edge rendering node viable (sub-ms doc reads, no network
   hop, full reload of a snapshot dir in seconds).
6. Blessed flow documented end to end: `powdb-cli backup` →
   `powdb-cli restore` → `powdb-server --readonly` (or embedded
   `openReadOnly`), with the swap-directory pattern for refresh: pull or
   restore the next snapshot beside the current one, open it, switch
   traffic, close the old dir. Atomic at the process level, zero engine
   changes beyond the read-only open.

### Deliberately deferred: live apply-while-serving in one dir

Serving reads from a directory while a separate process applies pulled
segments requires a reader-visible snapshot boundary (generational pages or
COW), cross-process invalidation, and live catalog reload: none exist, and
all three cut against the engine's core wins (in-place updates, compiled
predicates over raw bytes, intra-process mmap coherence). This is the same
class of tradeoff as multi-writer MVCC and stays decision-gated. The embedded
single-process replica (one handle applies segments and serves
`queryReadonly`) already exists for the live-tail case, and the
swap-directory pattern covers the edge-serving case with tier 1 alone.

### Tradeoffs (flagged)

- Read-only serving is stale-by-design between snapshot swaps; that is the
  point (published content), but the docs must say it plainly.
- A snapshot with unrefreshed materialized views will reject those queries
  rather than silently escalating. Correct, but a behavior change from the
  read-write path that operators must learn once.

### Acceptance

- Two read-only processes plus the CLI serving the same restored dir
  concurrently; a read-write open against a dir with live readers refuses.
- kill -9 during read-only serving: no dir mutation ever (verify by hash).
- Swap-directory refresh demo under load with zero failed reads.

## Lane D: null-vs-missing: migration, not mutation

Research confirmed the collapse points precisely:

- Legacy string frame: `Value::to_wire_string` renders Empty, `Json(null)`,
  and `Str("null")` identically (types.rs:95-115). The frame itself has no
  type discriminator and a golden byte-identity test pins it.
- Scalarized `->` leaf: `pj1_scalarize` maps a JSON null node to
  `Value::Empty` (executor/eval.rs:508), so missing-vs-JSON-null is lost
  **before any wire format**, including the native one. `json_type()`
  distinguishes them only because it inspects the raw PJ1 node.

Decisions:

1. **Do not retrofit type tags into the legacy frame.** It breaks the
   append-only protocol doctrine, every existing decoder, and the golden
   test, for a distinction the native frames already carry. Rejected.
2. **Publish the migration path as the fix**: the ORM-implementer spec (Lane
   E) plus client docs steer drivers to the native raw API, which is the
   sanctioned lossless surface. The legacy protocol is documented as
   string-typed with `"null"` ambiguity, frozen, and not deprecated out from
   under anyone.
3. **Do not add a JSON-null Value variant** to fix the scalarized-leaf
   collapse. A new `Value` variant ripples through ordering, grouping,
   index NULLS-LAST semantics, storage encoding, and every wire and client
   surface: a large risk for a distinction `json_type()` already recovers
   and that whole-document projection preserves. Documented as the escape
   hatch instead. Revisit only if a concrete workload cannot express itself
   with `json_type()`.
4. Optional bridge if a legacy-locked driver materializes: a Connect
   capability byte (the Connect frame already extends by appended optional
   fields) that opts a connection into distinct legacy rendering. Speced but
   not scheduled.

## Lane E: ORM/driver-implementer mapping spec + DX debts

1. **`docs/integrations/powql-for-drivers.md`** (public): the stable mapping
   surface a driver author needs without reverse-engineering from `--help`:
   path filter/order/group syntax, index DDL incl. expression indexes,
   parameter binding, the native typed frames (cell format, TypeIds, PJ1),
   explain output shape and its stability contract, admission/transaction
   semantics (FIFO queueing, bounded join rejection, cancellation errors),
   and the error taxonomy. Versioned; changes called out per release.
2. **npm client CHANGELOG is stale at 0.8.0** and ships in the tarball.
   Backfill 0.9→0.13, and extend `scripts/check-version-consistency.sh` to
   require `clients/ts/CHANGELOG.md` to mention the workspace version so it
   can never rot silently again.
3. Keep investing in `explain` (it is how the conjunction gap was found and
   quantified downstream in minutes): Lane A's "explain shows the executed
   plan" is the concrete next step.

## Sequencing and shape of the release

Lanes A-D are independent; Lane E's spec depends on A (explain) and B (the
JS-value union) landing first for accuracy.

- Wave 1 (parallel): Lane A (engine) + Lane B (facade/addon) + Lane D docs
  decisions + npm CHANGELOG fix.
- Wave 2 (parallel): Lane C (read-only mode) + Lane E spec.
- Gate: full workspace + clients green, Depot bench (including the new
  conjunction workload), read-only concurrency/kill -9 evidence, addon
  type-matrix tests, three-way validation re-run downstream.

Version: v0.14.0. Dev-state metadata (workspace 0.14.0, Next-release banner,
supported-series table) flips at branch start per the state-aware
`check-version-consistency.sh`.

## Explicit non-goals for v0.14

- Multi-writer MVCC (permanent non-goal; conflicts with compiled predicates,
  mmap scanning, and in-place updates).
- Live apply-while-serving replicas in a shared dir (decision-gated, see
  Lane C).
- Table statistics / cost-based planning (heuristic + probe is sufficient
  for the measured shapes; revisit with data).
- Legacy wire frame changes of any kind.
